## 第二轮：真机验证后修的问题

用户把手机接上后，真机验证立刻暴露出四个自动化测试没能覆盖的问题（9~12 号缺陷，见上表）：

1. **章节丢失（最严重）**。用户自己的《凡人修仙传》有 2445 章，导入后只剩一百多章。
   根因是我那个「章节序号必须递增、相邻跨度 ≤50」的过滤器：这本书 2255 章的标题是
   `第九卷 灵界百族 第一千四百二十二章 须弥洞天图` 这种**卷号章号同行**格式，正则抓到的是
   **卷号**（11），过滤器发现 11 小于上一个章号，就把后面的章节整片丢弃。修复方式是
   **彻底删掉这个过滤器**：多一条目录误报只是难看，丢掉九成章节是灾难，两者代价完全不对称。
   顺带把「结尾标点」检查收紧到只作用于**无分隔符的紧凑写法**（`第5章 凶手是谁？` 这种带
   分隔符的真实标题不会再被误杀），标题长度上限从 40 字放宽到 60 字。

   为了不让这次修复拖慢索引，还把逐行解码改成了**复用字符缓冲**：原先每行都建一个 String
   （100MB 小说上百万行 → 上百 MB 垃圾），现在只有真的命中章节规则才建 String。
   UTF-8 基准反而从 254ms 降到 215ms，峰值堆从 18.9MB 降到 15.2MB。

2. **上下滚动阅读**（用户要求，现在是默认阅读方式）。原来的实现只有左右翻页。
   滚动模式的做法是：整块文字**只用一个画布一次画完**，装在滚动容器里；滚动偏移直接换算成
   字符偏移来记录进度（比「第几页」更准）；滑到底自动接下一块 / 下一章。

   中间踩了三个坑（10~12 号缺陷）：手势层盖在列表上面导致完全滑不动、自动续接被提前组合
   触发导致自己乱跑、按页切片绘制导致后面全白。三个都是真机上才能发现的问题，也都补了
   回归测试（`scroll mode follows the visible page and continues to the next part`、
   `scroll mode does not advance by itself`）。

## 第三轮：跨章连续拼接（滚动轨道）

用户反馈「滑到章末尾接下一章太割裂」。原来的实现一次只在内存里放一块，滑到末尾就换成下一章、
滚动位置归零 —— 视觉上就是硬切。改成一条**滚动轨道**：

| 设计点 | 做法与理由 |
|---|---|
| 轨道内容 | 按顺序排好的若干块（每块 = 一章内 32KB 的一段，中文小说里通常正好是一整章），界面把它们竖着一个画布一块地排下去 |
| 预取时机 | 滚动位置距末尾还有**一屏**时就预取下一块。所以跨章时新内容早已排好在下面，用户滑过接缝看不到任何跳变 |
| 连续性不变式 | 相邻块在文件里必须**字节首尾相接**（上一块的 `endByte` 正好是下一块的 `startByte`）。这条有专门的测试盯着，断了就直接失败 |
| 内存上限 | 轨道最多 3 块，超了从前面丢。每块通常是一整章，所以用户往回翻两三章内容都还在，而内存里始终只有 3 份排版 |
| 坐标一致性 | 滚动位置换算成「第几块 + 块内字符偏移」，顶部条、进度、书签、划线全部以**可见的那一块**为准，滑过章界时它们自动跟着变 |
| 排版变化 | 改字号/行距后轨道里其它块还是旧排版，所以只保留当前这一块（位置不动），不会出现新旧排版混在一屏里 |

新增测试：
- `scroll track keeps chunks contiguous so chapters join seamlessly` —— 盯住上面那条字节相接的不变式
- `scroll track window is bounded and position follows the visible chunk` —— 窗口上限 + 位置跟随

**真机确认（2026-10-05，vivo 手机）**：逐次滑动直到章节名变化（1433 → 1434），再往回滑一屏，
同一屏里同时看到了 **1433 章结尾 + 原文的 `----------` 分隔线 + `第九卷 灵界百族 第一千四百三十四章 地渊守卫`
标题 + 1434 章正文**，而页脚仍显示 `1433 章 12/12`（因为视口顶部还在上一章）——
上一章尾巴留在上方、新章标题从下方自然滑入，**没有任何跳变**。证据截图：`device-evidence/B4-seam-back.png`。

## 第五轮：往上也能连续翻（0.2.1）

用户提出「从目录跳章之后，往回滑到章首就停住了」。补上**反向预取**：轨道头部也能接上一块，
往上滑会接住上一章的结尾 —— 和往下滑完全对称。

做法上换了实现方式，这一轮也因此抓出两个真 bug：

| 缺陷 | 现象 | 根因与修法 |
|---|---|---|
| 14 | 窗口收缩时**把用户正在读的那一块丢掉了** | 超限就无脑丢头部，而用户读的恰好是头部那一块，列表为保持可见项只能跳走 —— 真机表现是「读着读着突然跳回本章第 10 页」。修法：按活跃块在窗口里的位置决定从哪一头丢，**正在读的块永不丢** |
| 15 | 打开书时**恢复出来的阅读位置丢失**（回到章首） | 「轨道重置后归位」的 effect 跑在列表还没有 items 时，`scrollToItem` 被夹到 0，位置观察者又把 0 回写进状态。修法：等 items 就绪再滚，并且归位落地前跳过一次位置回写 |

同时把「手工补滚动偏移」换成了 **LazyColumn 稳定 key 锚定**：往头部插入内容时 Compose 自己
保持可见位置不动。我原先手工补偏移（`scrollBy(高度)`）在时序上不可靠 —— 新内容还没排好时
会被夹住，于是反复触发预取、画面乱跳。**标准做法一行都不用手算，这就是该抄别人代码的地方。**

**真机验证（2026-10-05）**，往回滑 8 次与往前滑 12 次的完整轨迹：

```
往回：6/15 → 4/15 → 3/15 → 2/15 →〔1445章 11/11〕→ 10/11 → 9/11 → 7/11
往前：7/11 → 9/11 → 10/11 → 11/11 →〔1446章 1/15〕→ 2/15 → 3/15 → 5/15 … 10/15
```

两个方向都平滑、单调、没有跳变，跨章落在正确的一侧（往回落在上一章**最后一页**，
往前落在下一章**第一页**）。空白页像素统计：4 张截图 4.33%~6.82%，没有空白。

### 一个必须记下来的教训：我的验证脚本自己错了

## 第六轮：主题真正"主题"了（0.3.0）

用户反馈两点，都成立：

> 「阅读设置里面的主题为什么设置了之后边框等页面没有跟着变？非常的突兀，而且应该再加几个颜色，比如樱粉」

| 问题 | 根因 | 修法 |

## 第七轮：自定义书籍封面（0.4.0）

用户提出「为什么到现在还没想起来自定义书籍封面」—— 确实该做，txt 小说本来就没有封面。

| 做法 | 说明 |
|---|---|
| 入口 | 每本书的「更多」菜单里：**设置封面 / 更换封面 / 移除封面**（后两项只在已有自定义封面时出现） |

| 处理 | 等比缩小到长边 ≤ 640px、JPEG 88%；API 28+ 用 `ImageDecoder`（自带 EXIF 转正），26/27 用 `BitmapFactory` + `ExifInterface` 手动转正；**先写临时文件再改名**，中途失败不会留下半张图 |

| 展示 | 书架封面在 IO 线程解码，并按「路径 + 文件修改时间」缓存（换了封面自然失效，滚动时不重复解码） |

### 数据库迁移：这次是真的动了用户的库

加 `coverPath` 字段意味着数据库要从 v1 升到 v2。这里**必须写迁移**（用 `fallbackToDestructiveMigration`
会清空用户几千章的索引和阅读进度），所以：

- 迁移就一句 `ALTER TABLE books ADD COLUMN coverPath TEXT`，另有测试直接跑这句 SQL，验证旧行（含 2445 章的那本）字段完好、新列为空
- **真机做了真实检验**：在已经装了 0.3.0（v1 库、有 2445 章和 27% 进度）的手机上直接升级安装 0.4.0 →
  App 正常打开、书和进度都在、logcat 无迁移异常

### 两个环境/工具层面的发现

1. **`ImageDecoder` 在 Robolectric 里是 stub**，会抛 `DecodeException: Only supported on Android`。
   顺手给 `decode` 加了回退：优先 ImageDecoder，失败退回 BitmapFactory。这不只是为了测试 ——
   生产环境上也多一条路。
2. lint 报了 9 个 error：`ImageDecoder` 系列需要 API 28（版本判断在调用处，lint 要求标在方法上 →
   加 `@RequiresApi(P)`），以及 `ProduceStateDoesNotAssignValue`（对 `by produceState` 的赋值误报）。
   后者我**没有用 suppress 掩盖**，而是换成语义等价的 `remember + LaunchedEffect`，不留歧义。

### 真机验证

设置封面（相册选图）→ 书架显示所选图片（正确裁剪成封面比例）→ 重启 App 封面仍在（持久化）→
移除封面 → 回退到生成的「凡」字封面并提示「已恢复默认封面」。截图：`U1`/`U2`/`U3`。

**一处诚实的缺口**：最后那次 lint 修复（`@RequiresApi` + produceState 改 remember）之后重新装包时

该流程在紧邻的上一版上验证过，而这次改动是行为等价的等价替换 + 注解补充。
