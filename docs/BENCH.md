# 墨阅 · 索引引擎基准报告（M2）

> 目的：证明「打开 100MB txt」不是靠运气，而是有实测数据支撑的硬指标。

## 测试环境

| 项 | 值 |
|---|---|
| 机器 | 12th Gen Intel i7-12700H / 15.6 GB RAM / Windows 11 |
| JDK | GraalVM JDK 21（Gradle 与测试 JVM） |
| 测试 JVM 堆上限 | **512 MB**（`maxHeapSize`，作为「内存有界」的硬约束） |
| 样本位置 | 系统临时目录 `%TEMP%\inkreader-bench\`（OS page cache 已预热） |
| 索引器参数 | 缓冲 1 MB，虚拟分章粒度 32 KB，全书共 3 份 100MB 样本 |

## 实测结果

| 场景 | 文件大小 | 索引耗时 | 识别章节数 | 峰值堆增量 | 驻留堆增量 | 吞吐 |
|---|---|---|---|---|---|---|
| GBK 有章节 | 100.2 MB | **266 ms** | 24 040 | 27.0 MB | 2.8 MB | 376.6 MB/s |
| UTF-8 有章节 | 100.1 MB | **254 ms** | 16 062 | 18.9 MB | 1.3 MB | 394.1 MB/s |
| GBK **单行无换行** | 100.0 MB | **128 ms** | 100（虚拟分章） | **2.5 MB** | ~0 MB | 781.3 MB/s |

另外：Room 批量写入 **23 000 行**章节索引耗时 **1 580 ms**（单事务，Robolectric 环境）。

## 与方案目标的对比

| 指标 | 方案目标 | 实测 | 结论 |
|---|---|---|---|
| 100MB 建索引耗时 | PC ≤ 5 s | 0.13 – 0.27 s | 达标（余量约 20 倍） |
| 索引峰值堆增量 | ≤ 32 MB | 2.5 – 27.0 MB | 达标 |
| 二次打开 | ≤ 300 ms | 走数据库查章节，不重扫文件 | 待 M3 真机确认 |
| 翻页耗时 | ≤ 16 ms | 待 M3 实测 | 待补 |

## 这些数字说明了什么

1. **内存确实有界，不是「刚好没爆」**。第 3 行是关键证据：整本 100MB 没有任何换行符，
   属于最恶劣的输入，它的峰值堆增量只有 **2.5 MB**，而且扫描行数为 0 —— 说明实现
   识别出「这是超过缓冲大小的超长行」后直接丢弃，**一个字节都没有被读进字符串**。
   一个 `readText()` 式的实现会在这里直接 OOM。
2. **章节偏移是精确的，不是估算**。GBK 与 UTF-8 两组样本的每个章节起点都被
   「seek 回去读一行」逐条校验（见 `ChapterIndexerTest`），24 040 个章节全部命中标题行。
3. **速度来自设计而非硬件**。扫描是单遍顺序字节流，只有长度 ≤120 字节的行才做解码，
   因此 100MB 正文里数十万个长段落**从未被解码过**，正则也只跑了极少数候选行。
4. **峰值堆增量包含 JIT 与临时垃圾**，真正的常驻结构是：1 MB 输入缓冲 +
   章节数组（24 040 章 ≈ 2.8 MB 常驻）。

## 手机上的预期（诚实说明）

以上全部是**本机 JVM 上的数字**，不是手机上的。中端 ARM 单核性能大致是本机大核的
1/5 – 1/8，加上存储更慢，预期 **100MB 小说建索引约 1.5 – 3 秒**，内存表现一致
（缓冲大小是常数，与文件大小无关）。真机数字待真机验证脚本补齐。
